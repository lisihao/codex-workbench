# Aegis and Code-as-Harness integration

The retained Aegis baseline was reviewed at commit `d5bda9fb9df0f94587283954f1c155816abe9002` (MIT), version 2.8.4, together with the prior local DSH Code-as-Harness and agent-development-governance Skills.

## Retained from Aegis

- simple tasks stay on a fast path;
- align non-trivial changes with the real owner and baseline before editing;
- diagnose before repair;
- add complexity only when it closes a current contract gap;
- distinguish fresh evidence from completion authority;
- report covered scope and residual risk;
- retire duplicate paths instead of stacking compatibility without evidence.

## Retained from Code-as-Harness

- repository-native executable gates outrank prose claims;
- governance, security, release, and deployment may require fail-closed full verification;
- attestation must match governed inputs when the project binds it;
- exact commit, package, and runtime provenance matters for formal delivery;
- recurring failures should become executable prevention when the evidence supports it.

## Workbench additions

- an active objective persists across later user steering unless explicitly replaced;
- safe independent DAG nodes should run in parallel with non-overlapping ownership;
- Evidence reuse binds the full declared input closure, not only a command name or success flag;
- a matching L3 fingerprint permits exactly one final full-gate execution.

## Deliberately excluded

- no mandatory full audit before every edit;
- no mandatory plan for tiny local work;
- no full verification after every individual requirement;
- no duplicate full suite merely because a commit changes HEAD;
- no universal attestation for ordinary development;
- no claim that an external platform plugin ran unless execution is observed.

Do not install Aegis wholesale merely to obtain these rules. Its broad router and overlapping method pack duplicate Workbench capabilities; install it only when the user explicitly wants that full system.
