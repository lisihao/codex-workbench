# One-time workspace lockfile handoff

This operation repairs a prerequisite of an existing blocked task. It does not create a replacement task, accept a worker result, enable automatic recovery, or grant the blocked worker additional write scope.

The task must already authorize `pnpm-lock.yaml`. A preview identifies the existing lockfile owner, the temporary handoff owner, the blocked node and attempt, accepted dependency inputs, and the manifest and lockfile fingerprints. Ambiguous ownership, active conflicting work, or changed inputs reject the operation.

Historical package-preparation failures may lack a dependency-input receipt. Recovery then requires the blocked result's content-verified pnpm materialization failure report and reconstructs accepted ancestor patches from the fixed task snapshot in a private Git index. The reconstructed tree must exactly match the source's staged tree; missing evidence, corrupt patches, changed ancestors or staged worker edits reject recovery. The live index, worker files and historical task result are not rewritten. Normal preparation now preserves its completed input receipt even if the subsequent package installation fails.

The preview lists up to 32 changed importer paths and reports the complete count and fingerprint. If `changed_importers_truncated` is true, the displayed list is incomplete; inspect the complete source plan before authorizing application.

`workbench_handoff_lockfile` is available through the existing authenticated Authority service. `preview` and `status` are read-only. `apply` requires the preview fingerprint and a stable request ID matching the Authority journal request ID. After an uncertain transport response, query that journal receipt and the handoff status; do not invent a new ID to retry.

Apply reserves temporary ownership and reconstructs a separate repair worktree from accepted inputs and the scope-checked existing source delta. Original worktrees and historical acceptance receipts are not modified. The importer editor supports the repository's generated pnpm lockfile format and adds missing supported workspace links only. Unsupported formats and third-party dependency changes are rejected rather than normalized or upgraded. The fixed offline frozen-lockfile check remains mandatory.

Dependency readiness and reusable-cache publication have separate outcomes. A successful offline frozen install with a complete worktree-local linker remains usable if publishing its optional cache template fails. The materialization receipt records that publication failure explicitly; it is not a cache hit. Installation failures or incomplete linkers still block readiness. The shared deadline remains bounded, and a subprocess timeout reports its remaining command budget, not a new total installation limit.

A lockfile overlay does not restore an earlier attempt's own implementation patch. When accepted work from an earlier attempt must be retained, verify its artifact identity and compatibility with the current accepted ancestor closure separately, and bind it through the governed recovery input before dispatch. An isolated compatibility check does not itself authorize a production state change or prove the next worker received the patch.

A later accepted-source repair may replace one of the overlay owner's accepted ancestors with a newer accepted attempt. The historical handoff receipt remains immutable. Replay may bind its application point to the newer closure only when the ancestor node sequence is unchanged, attempts advance monotonically, and a same-attempt patch identity is unchanged. Normal blocked-worktree recovery selects that current replay point before applying the historical dependency input; it does not require the superseded attempt tuple to reappear in the reconstructed tree. The reconstructed worktree must then match the handoff's sealed manifest fingerprints and either its original lockfile bytes or the exact repaired bytes already produced by an earlier applicable handoff. The latter case is an idempotent no-op, not a new lockfile derivation. A graph change, attempt rollback, manifest change, or any other lockfile content still rejects replay. Descendants additionally require the refreshed owner result to record the same handoff identity.

Successful verification atomically associates the new lockfile content artifact with the original task input and returns temporary ownership. It does not queue the node or advance its attempt. The task coordinator separately reviews the receipt and performs the normal continuation. The derived input receipt records the handoff so retry, downstream, and final-verifier worktrees reproduce the same input without attributing the lockfile change to the original worker.

The fixed D integration scope amendment may change the task contract after a ready handoff was recorded. In that one path, the existing `task.blocked_integration_scope_amended` event is the rebinding proof for every still-ready overlay in the same task, including an accepted ancestor's overlay inherited by D. Its old and new contracts must demonstrate a monotonic `allowed_scope` addition with every other contract field unchanged. The ready-event identity, accepted ancestor receipt, source fingerprint, manifest fingerprint, and lockfile artifacts remain byte-for-byte unchanged; only the contract digest and task revision are derived from the amendment. Recovery upgrades a recorded dependency-input receipt from that validated event before lineage checking. Missing events, altered content identities, non-scope contract changes, or an unrelated contract still fail closed. The ready event, scope-amendment event, and historical worker result remain immutable.

Failure, cancellation, and interrupted-operation reconciliation never publish an unverified input. Separate journal IDs identify reconciliation or cancellation operations targeting the original handoff ID. Releasing a reservation fences a late original runner from committing a ready receipt; it does not claim to terminate a subprocess that may still be writing only its isolated worktree.

The final verifier remains the only task-acceptance authority. A verified lockfile handoff proves that prerequisite repair, not completion of the original task or a new application release.

Ledger schema 15 fences older coordinators that do not recognize temporary lockfile ownership or derived dependency-input receipts. Deployment must use the existing cooperative drain and consistent backup protocol. Rolling back code alone against the new ledger is unsupported; restore only a verified matching backup at the repository's safe point, without discarding subsequent task writes.
