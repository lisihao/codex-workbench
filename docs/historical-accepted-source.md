# Historical accepted source recovery

Historical accepted source recovery preserves a worker's previously accepted implementation when its current attempt is blocked before completing new work. It selects an explicit accepted event for the same task and node, rather than guessing from the latest message or rewriting the implementation with another worker.

`workbench_restore_accepted_source` exposes `preview`, `apply`, and `status`. Preview binds the accepted event, verified patch and dependency-input artifacts, the historical ancestor evidence, and the current task contract, revision, attempt, allocation, accepted ancestors, and ready lockfile overlays. Apply requires that fingerprint and the same current state; it authorizes and queues one next attempt through the existing Authority request journal. Status observes that request without replaying it. Repeating an identical completed request returns its original receipt; changing the payload under the same request ID is a conflict.

The historical dependency input and current input have different roles. The former proves what was accepted at that event. The latter defines the dependency closure the next attempt must use. Preparation reconstructs the current accepted closure and ready lockfile overlays in a fresh owned worktree, then applies the exact historical worker patch. A missing or incompatible artifact, unsupported historical lineage, changed current source, or patch conflict blocks execution rather than dropping either input.

The `historical-accepted-source-v1` binding uses the existing recovery record, event log, scheduler claim, allocation assignment, and lease checks. It does not add a table, migration, scheduler, permission grant, or new task. Assignment supersedes the current blocked allocation, not the historical accepted allocation. Historical results and original worktrees remain intact. Pause, cancellation, and stale leases are checked before assignment and again before dispatch after dependency preparation.

Repository-isolated API and consumer validation proves the candidate preparation path; it does not change a production task or authorize deployment. Production use requires an installed matching API/coordinator version and a fresh preview followed by the owning coordinator's CAS. Older coordinators must not be used to execute an unresolved binding they do not understand.
